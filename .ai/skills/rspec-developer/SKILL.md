Adapted from `java-unit-test-developer` (JUnit5/Mockito/AssertJ) in the reference
project — same posture (one concept per test, `sut`-style naming, no over-mocking),
translated to what this repo actually has: RSpec only, no Minitest anywhere in
`pis-gogrow` (confirmed: no `test/` directory exists).

## Scope — read this first

- Inertia-specific assertions on a controller/request spec (component name, props,
  flash after redirect) → use `pis-gogrow:inertia-rails-testing`'s matchers
  (`render_component`, `have_props`, `have_flash`), never `inertia.props` directly,
  and never forget `follow_redirect!` after a POST/PATCH/DELETE — that skill already
  owns this ground, don't duplicate it here.
- A spec that drives a real browser (`type: :system`) → `capybara-smoke-check` for a
  throwaway check, `capybara-system-suite` for a committed regression spec.
- Everything else backend-side (model specs, mailer specs, helper specs, the
  non-Inertia parts of request specs) → this skill.

## Spec types and where they live

```
spec/models/*_spec.rb      # validations, associations, scopes, callbacks
spec/requests/*_spec.rb    # one file per controller; type: :request
spec/mailers/*_spec.rb
spec/helpers/*_spec.rb
```

`config.infer_spec_type_from_file_location!` is on, but existing specs still pass
`type: :request` explicitly in the `describe` block (`RSpec.describe "Accounts",
type: :request do`) — match that, don't drop it just because it's inferrable.

Every spec file starts with `# frozen_string_literal: true` (RuboCop-enforced,
`Style/FrozenStringLiteralComment`, no exceptions).

## Fixtures vs factories — not interchangeable here

**`User` uses fixtures** (`spec/fixtures/users.yml`, loaded via
`config.fixture_paths`, `config.use_transactional_fixtures = true`) — reference
named fixture rows (`users(:one)`), don't build a `User` with `FactoryBot.create`.

**Everything else uses `factory_bot`** (`spec/factories/*.rb`, one file per model,
already wired via `config.include FactoryBot::Syntax::Methods`). Use `Faker` for
values whose specific content doesn't matter instead of hardcoded strings — the
gem is in the Gemfile precisely for this; an existing factory like `accounts.rb`
hardcoding `amount { "9.99" }` is fine only when the test actually cares about that
exact value, not as a general pattern to copy.

Don't reach for `create()` when `build()` or `build_stubbed()` covers the test —
only hit the database when the spec needs a persisted record (an association
query, a uniqueness validation, a callback).

## Never hand-edit the `== Schema Information` block

`annotaterb` (`.annotaterb.yml`) appends a schema comment to the bottom of **both**
model files and factory files. If a migration changes a column, the annotation is
regenerated by the annotaterb task, not edited by hand in the spec/model/factory —
a hand-edited annotation that drifts from `db/schema.rb` is a review finding, not a
formatting nitpick.

## Validations and associations: shoulda-matchers, not hand-rolled

`shoulda-matchers` is already configured (`spec/support/shoulda_matchers.rb`). Use
the one-liner matchers instead of writing `expect(model.errors[:x]).to include(...)`
by hand:

```ruby
it { is_expected.to validate_presence_of(:owner) }
it { is_expected.to belong_to(:owner) }
it { is_expected.to have_many(:orders).through(:order_accounts) }
```

## Auth in request specs

`spec/support/authentication_helpers.rb` defines **two different** `sign_in`/
`sign_out` implementations, auto-included by spec type — don't reimplement either:

- `type: :request` → sets a signed `session_token` cookie via `cookies[...]`.
- `type: :system` → sets the same cookie via `page.driver.set_cookie(...)`.

Calling the request-spec version from a system spec (or vice versa) silently does
nothing useful — always check the file already includes the right module for its
`type:`, don't copy a `sign_in(user)` call across spec types without checking.

## Filling in a generated stub

New controllers/models generate specs as a single `pending "add some examples (or
delete) #{__FILE__}"` line. When asked to add coverage for one of these: replace
the `pending` line entirely, don't leave it dangling next to real examples — a
`pending` alongside passing examples in the same file reads as unfinished work.

## Running

```bash
bin/rspec                              # everything bin/ci runs (via db:test:prepare spec)
bin/rspec spec/requests/users_spec.rb   # one file
bin/rspec spec/requests/users_spec.rb:12  # one example
```
